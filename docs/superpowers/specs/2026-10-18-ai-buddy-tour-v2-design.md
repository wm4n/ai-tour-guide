## 1. 意圖

一個陪你出遊的 AI 好友。出門時手動啟動一次，之後它會自己看位置和時機，主動用自然的台灣中文跟你聊身邊的景點和事物。你想問的時候，用說的（偶爾拍照）問它。

這次重啟的理由：

1. 舊版從未完成到能帶出門用，沒有包袱。
2. 改用使用者自己的 **Claude Pro 訂閱**，取代按 token 計費的 LLM API：**訂閱額度用完就停，不會再多花錢**。
3. 語音要「有人味」：有抑揚頓挫，像朋友在旁邊講話，不能有機器感、念稿感。

**為什麼要做自己的 App，而不是用聊天 App（Telegram 等）當介面**【使用者決定】：聊天 App 收到語音訊息只會跳通知，不會在口袋裡自動播放。「放口袋，它自己開口」是這個專案和聊天機器人最大的差別。

## 2. 一次散步的樣子

使用者在台北大稻埕附近散步，iPhone 放在口袋、戴著耳機。打開 App 按「出發」，好友說「好，我們出發吧！」，之後就不用再操作。

- 按下出發時，主機先把起點周邊一整區的內容準備好。之後一邊走，一邊為前方的景點準備內容。
- 走到附近時，好友自然地開口：「你看左邊那棟紅磚房子……」，講三、四十秒。兩段介紹之間至少隔 3 分鐘；沒有值得講的東西時，它就安靜陪你走。
- 使用者在聽音樂時，音樂會先調小聲，講完再恢復。
- 使用者想安靜一下（例如吃飯、跟人講話）時，按耳機或鎖定畫面的暫停鍵，主動介紹就會暫停；再按一次恢復。
- 使用者想問時，拿出手機按住說話：「那間廟拜的是誰？」好友馬上先回一句「好，我來查一下，你稍等我一下」，然後開始回答。如果正在講一段介紹，回答完會從中斷的那句接著講。
- 偶爾拍一張照片問「這是什麼」，或問「附近有什麼好吃的？」。需要上網查時，好友會說「我上網查一下，可能要多等一下」。
- 「剛剛那個再多說一點」也是用說的問。
- Claude 額度用完時，好友說「額度用完了，我先安靜陪你走」；額度恢復後說「我恢復了，我們繼續」。
- 連不上家裡的主機時，好友說「我連不上家裡的電腦了，先安靜一下，連上了再跟你說」。

## 3. 目標、非目標、反目標

### 目標
- **G1** 主動介紹：由位置與時機驅動，使用者不需操作。
- **G2** 語音問答：以眼前事物為主，偶爾問附近吃的；支援拍照提問。
- **G3** 語音自然：KittenTTS 2 搭配固定的真人參考聲音，講台灣中文。
- **G4** 零額外費用：LLM 只走 Claude Pro 訂閱；其餘服務都在免費額度內，並設上限。

### 非目標（這個里程碑不做）
- Android 版（先做 iPhone）。
- 給其他人使用或上架。
- 預先規劃行程模式。使用者大多「走到哪看到哪」，行程不可靠。
- 多種人設切換。只有一位好友，舊版的 5 種人設不沿用。
- 開車模式。
- 中文以外的語言。
- 地圖畫面。
- 吃飯時間主動推薦餐廳。
- openab（延後，見第 5.3 節）。

### 反目標（技術上能動，但做成這樣就算失敗）
- 講話像機器或像在念稿。
- 話太多，每經過一個招牌就開口。
- 一開口就講好幾分鐘。
- 用了按量計費的 LLM API、usage credits，或是在使用者不知情下產生 Google 費用。
- 額度用完時改用其他付費方式繼續。
- 播出聽不懂的語音，例如類粵語腔或亂碼。

## 5. 架構

```
iPhone（Flutter，app/）
  ├─ 定位（含行進方向）、時機判斷、播放佇列、背景音訊、鎖定畫面控制
  ├─ 語音辨識（先試 iOS 本機 zh-TW，不行改 Apple 線上辨識）
  └─ 拍照
        │  Tailscale（只有使用者的裝置能連）
        ▼
家中主機（M3 → M6，macOS 原生）
  ├─ Buddy Host 服務（Python，新寫，只聽 Tailscale 介面）
  │    ├─ 景點探索：Overpass、Wikipedia geosearch／摘要
  │    ├─ 內容準備編排：決定為哪些景點準備內容，先整理資料，再請 Claude 寫稿
  │    ├─ 旅程記憶：這趟去過哪裡、講過什麼、查到什麼；跨趟永久保存
  │    ├─ 寫稿前處理：數字轉中文、去日文假名、切句
  │    ├─ TTS：KittenTTS 2（MPS），問答優先於主動介紹
  │    ├─ 自動驗收：Whisper 轉回文字比對 CER，失敗就換 seed、拆句
  │    ├─ 快取：景點資料、稿子、語音檔
  │    ├─ 用量記錄與報告
  │    ├─ MCP 工具伺服器：places_nearby（Google Places，API key 只放在主機）
  │    └─ 對手機的 API：位置回報、待播內容、提問、拍照提問、事件推送
  └─ Claude Code（headless，Claude Pro 訂閱）
       └─ 工具：WebSearch、WebFetch、places_nearby（MCP）
```

### 5.1 分工原則【使用者決定】
- 手機負責「什麼時候講」：時機、播放、使用者互動。
- 主機負責「講什麼」：查資料、寫稿、合成、驗收、快取、記憶。
- 手機只連 Buddy Host 這一個入口。

### 5.2 呼叫 Claude 的方式【使用者決定】
- Buddy Host 用 `claude -p` 呼叫 Claude Code，使用 `CLAUDE_CODE_OAUTH_TOKEN`（來自 `claude setup-token`，放在主機本機，不入 repo）。
- **每次呼叫都是新的對話**，不用 `--resume`。官方文件指出，對話越長，越消耗額度。旅程上下文由 Buddy Host 以精簡摘要附在每次 prompt 中，內容包括：這趟去過哪裡、講過什麼、附近景點資料。
- 用 `--output-format stream-json` 取得串流文字、`modelUsage`（含 subagent 的用量），以及 `rate_limit_event`（`status`、`resetsAt`、`utilization`）。
- 圖片：存成主機上的檔案，在 prompt 裡寫路徑，讓 Claude 用 Read 工具讀取；或用 `--input-format stream-json` 傳 image block【未驗證】。
- 冷啟動延遲的社群回報約數秒到 20 秒【未驗證】。若太慢，可以評估維持一個長駐的 stream-json 行程。但要注意：在同一個行程裡連續送多個回合，就等於是同一段對話，會越來越吃額度。這部分【builder】決定。
- `--bare` 不讀 OAuth 憑證，**不可使用**。
- 模型：寫稿與問答預設用 Sonnet，判斷類工作（挑景點、判斷問題類型）用 Haiku，都可以在設定裡切換。Buddy Host 必須拒絕 Fable。

### 5.3 openab 延後【使用者決定】
2026-10 查證結果：
- openab 沒有 macOS 版本的 binary，只能用 cargo 編譯（需要 `--features acp`），或用 Docker 執行。
- ACP WebSocket 在 Phase-1 **不串流**，整段回覆最後才一次送出。
- **不接受圖片**（`promptCapabilities.image:false`）。
- 一個回合超過 180 秒就逾時。
- 額度錯誤很可能被壓平成一般文字。

因此第一個里程碑不使用 openab。Buddy Host 與 LLM 之間的介接要做成可替換的一層，等 openab 補上串流與圖片支援後，可以再評估換回去。

## 6. 好友的個性與寫作規則

### 6.1 個性【使用者決定】
以使用者自己寫的「名花之里」導覽稿為範本：
- 原文：`docs/spikes/2026-10-18-kittentts2/texts/35_nabana_original.txt`
- 前處理後的版本：`texts/35_nabana.txt`

1. 用「我們」，是一起旅行的同伴，不是站在台上的導遊。
2. 記得這趟剛去過哪裡，會拿來對比、串連。
3. 有自己的看法。
4. 先講有趣的反差或故事，數字點到為止。
5. 給實用建議（幾點來最好、待多久）。
6. 知道什麼時候閉嘴。
7. 偶爾反過來問使用者，但要非常節制。
8. 聲音是女生（F2 參考錄音）。
9. 經過以前介紹過的地方時，換個角度講（「上次跟你說過它是茶行，今天講點別的」），不是不講。

### 6.2 設定檔【使用者決定】
個性描述、寫作規則、範本稿放在 repo 的一個設定檔裡（不含敏感資料）。Buddy Host 每次呼叫都讀這個檔，改了就生效，不用重新編譯 App。

### 6.3 長度
主動介紹預設每段 30 到 45 秒。想多聽時，使用者用說的問「再多說一點」。

### 6.4 寫作規則（試聽實測得出，寫進給 Claude 的指示，Buddy Host 前處理時再用程式保證一次）

| 規則 | 原因 |
|---|---|
| 所有數字轉成中文：年份逐字唸「二零二七年」，數量用「兩百公尺」 | KittenTTS 2 對非英文必須設 `normalize=False` |
| 長串日期、多個數字的句子要拆短或改成口語（「十月中到明年五月底」） | 長串日期 4 次全部失敗，其中 2 次產生 40 秒的亂碼 |
| 移除日文假名，必要時只留羅馬拼音 | 模型多半唸不出假名 |
| 避免「欸、啊、喔、吧、一下下」等語助詞，親切感靠句型和用詞營造 | 這些詞會讓模型跑成類粵語腔 |
| 英文單字能用中文就用中文 | 夾英文聽起來怪 |
| 依「。！？」切句，每段約 90 字以內 | 內建的切句只認 ASCII 標點 |

**語助詞實測（2026-10-19，#16）**：12 個候選詞 × 3 句 × 3 個 seed，用驗收器（Whisper CER ≤ 0.20）量測。完整數據與限制見 [`docs/spikes/2026-10-19-particles/`](../../spikes/2026-10-19-particles/README.md)。

| 類別 | 詞 | 依據 |
|---|---|---|
| 避免（聽感） | 欸、啊、喔、吧、一下下 | 使用者試聽時聽到類粵語腔；CER 量不出口音，待人耳確認 |
| 避免（驗收失敗率高） | 哇、欸、呢 | 句首感嘆詞與句尾「呢」的過關率只有 2/9～6/9 |
| 可以用 | 對了、而且、其實、你看、啦 | 過關率 7/9～8/9，失敗只偶發在單一 seed，管線換 seed 重試可兜底（整段被跳過的機率 ≤ 0.2%） |

「啊」的 CER 九次全過（最好），但因為量不出口音，仍維持避免，等人耳確認。結論已寫進 `host/config/buddy.md` 的寫作規則。

## 7. 主動介紹流程

0. 按「出發」時，先把起點周邊一整區的內容準備好【使用者決定】。這是依當下所在位置準備，不違反「不做預先規劃行程」的非目標。
1. 手機在背景持續定位，定期把位置與行進方向回報給 Buddy Host。
2. Buddy Host 找出附近候選景點（OSM + Wikipedia），範圍包括景點、古蹟、建築，以及**有故事的老店和知名店家**【使用者決定】。排序依據：在行進方向前方、有 Wikipedia 條目、距離近、不重複主題。舊 backend 的景點選擇規則與過濾規則可以移植。
3. 只為最有可能經過的前一兩個景點準備內容。流程：
   - Buddy Host 先整理好 Wikipedia 摘要和 OSM 資訊，交給 Claude 寫稿。資料太少時，Claude 才自己上網補【使用者決定】。
   - 寫好的稿子經過前處理、合成、驗收後存進快取。
4. 手機依時機播放：
   - 兩段介紹之間至少隔 3 分鐘【使用者決定】。
   - 舊 Flutter 的其他時機規則可以當起點，例如移動距離太小、候選景點重複時就跳過，以及佇列裡的內容過時就丟掉。
5. 沒有好內容就安靜。
6. 介紹過的景點會永久記錄。下次經過時換個角度講，必要時才跳過【使用者決定】。

**一趟的範圍**：
- 從按「出發」到按「結束」算一趟。
- App 被系統關掉或手機重開，重開 App 時如果距離上次活動不到 2 小時，就接續同一趟；超過 2 小時就算新的一趟【使用者決定】。

## 8. 問答流程

1. **發問方式**：第一個里程碑用螢幕上的按住說話按鈕【使用者決定】。
   - 下一步：iPhone 14 Pro 沒有動作按鈕；iOS 也不允許 App 在背景開始錄音，所以 AirPods 觸發做不到。
   - 里程碑之後可以評估「背面輕點」（Back Tap）、Siri、鎖定畫面控制項加上 `AudioRecordingIntent`（iOS 18 以上，錄音期間需要顯示 Live Activity）【未驗證】。
2. **語音辨識**：先試 iOS 本機的 zh-TW 辨識（`requiresOnDeviceRecognition`），不行就改用 Apple 線上辨識（免費，語音會送到 Apple）【使用者決定】。要用實機確認本機辨識是否支援 zh-TW；iOS 26 的 SpeechTranscriber 也可以評估。
3. **立即回應**：手機馬上播放事先合成好的短句（第 9.3 節）。
4. **送到主機**：Buddy Host 把問題連同目前位置、行進方向、附近景點資料、旅程摘要一起交給 Claude。
   - 「眼前、左右」預設用行進方向（GPS 算出的移動方向）推算；使用者拿著手機拍照或看畫面時，改用指南針【使用者決定】。
5. **回答**：第一句要短，合成並驗收好就先播，後面的邊播邊合成。
6. **吃的問題**：Claude 自己判斷要不要呼叫 `places_nearby` 工具查 Google Places【使用者決定】。
7. **拍照提問**：手機上傳照片，Buddy Host 存成檔案，交給 Claude 看圖判斷。
8. **打斷**：發問時，正在播的介紹先暫停，答完從中斷的那句接著講【使用者決定】。
9. **追問**：「再多說一點」走一樣的問答流程，旅程摘要裡會帶著「剛剛講的那段」。

### 延遲
- **目標**：問完到聽到真正的答案 ≤ 10 秒。要上網查的問題可以超過，但要先說「我上網查一下」。
- **10 秒不是第一個里程碑的驗收條件**。在 M3 上，合成一句 3 秒的話要 10 到 12 秒，驗收每句再加 3 到 14 秒。要達到目標，得靠 M6，或以下優化：llama.cpp 版本、參考錄音只編碼一次、更快的驗收用 ASR。
- **問答也要經過自動驗收**【使用者決定】：品質優先。等待的空檔用事先合成的短句填補。

## 9. 語音管線

### 9.1 合成
- 引擎：`kittenml` 的 KittenTTS 2，參數 `weights="packed"`、`decoder="default"`，在 MPS 上跑。不能用 CPU：CPU 的 RTF 約 21，而且輸出異常。
- 參考聲音：F2 片段（`ref_24k.wav`，13.4 秒）加上逐字稿，放在主機本機的 `~/.buddy-host/voice/F2/`，不入 git。**必須傳 `reference_text`**。
- 參考錄音的使用限制：
  - 取自公開 Podcast，是公眾人物的聲音，只限使用者本人使用。
  - 若 App 將來給任何其他人用，必須換成有授權的聲音。
- 排程：Mac 只有一顆 GPU。問答優先：正在合成的主動介紹在句子之間暫停，先讓問答合成【使用者決定】。

### 9.2 自動驗收
- 驗收原型在 `docs/spikes/2026-10-18-kittentts2/run_r3_autocheck.py`。
- 流程：逐句合成，用 Whisper 轉回文字，經 OpenCC 轉成簡體並去掉標點後計算 CER。CER 超過 0.20 就換 seed 重做，最多 4 次。
- **必修**：比對前要把阿拉伯數字和中文數字統一。
- 4 次都不合格時：先用程式把句子拆短再重試，還是不行就跳過這句【使用者決定】。原則是寧可少講一句，也不要播出聽不懂的語音。
- 驗收用的 ASR（Whisper small 在 CPU 上、mlx-whisper 等）【builder】決定，但要量測它跟 TTS 搶資源的影響。

### 9.3 固定短句【使用者決定】
每句多跑幾個 seed，由使用者挑選後打包進 App：
1. 「好，我來查一下，你稍等我一下。」（問答開頭）
2. 「這個問題很好，讓我想一下。」（問答開頭替換）
3. 「我想想怎麼說比較好。」（答案還沒好時補一句）
4. 「我上網查一下，可能要多等一下。」（需要上網查時）
5. 「額度用完了，我先安靜陪你走。」
6. 「我連不上家裡的電腦了，先安靜一下，連上了再跟你說。」
7. 「好，我們出發吧！」（按出發時）
8. 「我恢復了，我們繼續。」（額度恢復或重新連上時）

### 9.4 已知效能（M3）
- 首次合成的 RTF 約 3 到 4；含重試約 11 倍。
- KittenTTS 2 和 Whisper 在同一個行程時，峰值記憶體 11.8 GB。

## 10. 景點資料與 Google Places

- **景點**：
  - Overpass API：遵守公用伺服器的政策，包括可識別的 User-Agent、退避、快取。
  - Wikipedia geosearch 與摘要：附合規的 User-Agent。
  - 舊 backend 的 Overpass、Wikipedia client 與 resolver 可以移植。
- **Google Places**（只用於吃的，以 MCP 工具 `places_nearby` 提供給 Claude）：
  - API key 只放在主機上。
  - Nearby Search 預設只取 Pro 欄位；評分、營業時間只對要推薦的少數店家另外查。
  - **GCP 防護**：在 APIs & Services → Places API → Quotas 把每日請求上限調低（建議每天 50 次），另設預算警示（例如 1 美元寄信）。預算只會通知，配額才會真的擋住。

## 11. 額度、用量與成本

- Claude Pro 的實際額度官方沒有公布。結構是每 5 小時重置一次，加上每週上限、Opus 與 Sonnet 各自的上限，claude.ai 和 Claude Code 共用。
- **不設每趟用量上限**【使用者決定】。這個訂閱也用在其他日常工作上，使用者想實測一趟會用掉多少、多久撞到上限。
- 省額度的原則：
  - 每次都開新對話。
  - 由主機先整理好資料。
  - 一次研究一整區。
  - 查過的不再查。
  - 寫稿用 Sonnet，判斷用 Haiku。
- **用量記錄**：
  - 每次呼叫 Claude 都記下用途、模型、時間、`modelUsage`，以及 `rate_limit_event` 的 `utilization`。
  - `total_cost_usd` 只是客戶端估算值，不是帳單。
- **用量報告**【使用者決定】：每趟結束時，主機產生一份報告檔；App 的結束畫面顯示摘要。
- **額度用完**：
  - Buddy Host 看到 `rate_limit_event` 的 `status=rejected`（或錯誤文字 `You've hit your … limit`）時，通知手機。手機播放固定短句 5，然後停止主動介紹與問答。
  - 依 `resetsAt` 時間（或定期用很輕的請求探測）確認額度恢復後，播放固定短句 8 並繼續。
- Google Places 用配額上限控制在免費額度內。

## 12. 主機維運【使用者決定】

- 關閉 Mac 的自動睡眠，並開啟「斷電恢復後自動開機」。
- 開機後自動啟動 Buddy Host 與 Tailscale；服務掛掉時自動重啟（例如用 launchd）。
- 出遠門前，把 Mac 插上電、蓋子打開（或接上外接螢幕後闔上）。
- Buddy Host 只監聽 Tailscale 介面。
- 主機上的設定與機密統一放在 `~/.buddy-host/`：OAuth token、Google API key、參考聲音。
- **連不上主機時**：App 播放固定短句 6，安靜地在背景重試；連上後播放固定短句 8。

## 13. App

- **新專案**：在 `app/` 開新的 Flutter 專案【使用者決定】。從舊 `flutter_app/` 複製可沿用的模組：
  - 定位、haversine
  - 音訊播放與 `TourAudioHandler`（audio_service）
  - Drift 本機資料庫、通知、設定、logging、麥克風錄音
  - 播放佇列的概念與時機規則
- Riverpod 一律用 Notifier／AsyncNotifier，不混用 StateNotifier。
- **畫面**（里程碑範圍）【使用者決定】：出發／結束、按住說話、拍照提問、目前播放的內容、主機連線狀態、額度狀態、結束時的用量摘要。不做地圖。
- **背景**：開啟 `UIBackgroundModes` 的 location 與 audio，定位權限要 Always。舊背景播放是 Android 優先的設計，iOS 要重新驗證。
- **音訊**：播放時降低其他 App 的音量（duck）；耳機或鎖定畫面的暫停鍵，對應「暫停主動介紹」【使用者決定】。
- **安裝**：開發時從 Xcode 直接安裝；出門驗收前上傳 TestFlight 內部測試版【使用者決定】。

## 14. 舊 repo 的處理【使用者決定】

- 舊 `backend/` 與 `flutter_app/` 搬到 `legacy/`，供移植時對照，v2 里程碑完成後刪除。
- 可以移植到 Buddy Host 的：Overpass／Wikipedia client、景點選擇與過濾規則、距離提示、句子切分。
- 整體淘汰的：FastAPI SSE、Gemini／Edge TTS providers、Cloud Run 部署。
- `openspec/` 只保留 v1 歷史。

## 16. 第一個里程碑的驗收條件【使用者決定】

> 在台北走一趟，好友能主動介紹景點，也能回答問題，就算過關。

- 主動介紹至少 3 段。
- 主機：開發與驗證先用 M3。若 M3 撐不住，例如 16 GB 放不下或速度跟不上，**驗收等 M6／32 GB 到手再做**，不為了 M3 做大規模優化。

- 播出的語音必須聽得懂，由自動驗收保證。
