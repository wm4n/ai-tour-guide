# AI Buddy Tour v2 設計

- 日期：2026-10-18
- 狀態：草稿，待使用者核准
- 取代：`2026-05-08-ai-tour-guide-design.md` 以及其後各 plan 的整體架構（舊設計保留作歷史參考）
- 試聽證據：`docs/spikes/2026-10-18-kittentts2/`

標記說明：**【使用者決定】** 是使用者在討論中明確選定的；**【我的提案】** 是我做的判斷，使用者尚未逐條確認，builder 可提出異議；**【未驗證】** 是推論或尚未實測的事。

---

## 1. 意圖

一個陪你出遊的 AI 好友。出門時手動啟動一次，之後它自己看位置和時機，主動用自然的台灣中文跟你聊身邊的景點和事物；你想問的時候，用說的（偶爾拍照）問它。

這次重啟的理由：

1. 舊版從未完成到能帶出門用，沒有包袱。
2. 改用使用者自己的 **Claude Pro 訂閱**（透過 openab）取代按 token 計費的 LLM API：**訂閱額度用完就停，不會再多花錢**。
3. 語音要「有人味」：有抑揚頓挫、像朋友在旁邊講話，不能有機器感、念稿感。

## 2. 一次散步的樣子

使用者在台北大稻埕附近散步，iPhone 放口袋、戴耳機。打開 App 按「出發」後就不用再操作。

- 快走近一個區域時，App 在背景先把附近值得講的景點查好、寫好、合成好語音。
- 走到附近時，好友自然開口：「你看左邊那棟紅磚房子……」，講三、四十秒。沒有值得講的東西時，它就安靜陪你走。
- 使用者想問時，用說的：「那間廟拜的是誰？」好友先馬上回一句「好，我來查一下」，然後開始回答。偶爾拍一張照片問「這是什麼」。
- 偶爾問「附近有什麼好吃的？」，這種要臨時查，等久一點也可以接受。
- Claude 額度用完時，好友說一句「今天的額度用完了」，然後安靜下來。

## 3. 目標、非目標、反目標

### 目標
- **G1** 主動介紹：位置與時機驅動，使用者不需操作。
- **G2** 語音問答：以眼前事物為主，偶爾問附近吃的；支援拍照提問。
- **G3** 語音自然：KittenTTS 2 + 固定真人參考聲音，台灣中文。
- **G4** 零額外費用：LLM 只走 Claude Pro 訂閱；其餘服務在免費額度內並設上限。

### 非目標（這個里程碑不做）
- Android 版（先做 iPhone）。
- 給其他人使用或上架。
- 預先規劃行程模式（使用者大多「走到哪看到哪」，行程不可靠）。
- 多種人設切換（舊版的 5 種人設不沿用，只有一位好友）。
- 開車模式。
- 中文以外的語言。

### 反目標（技術上能動，但做成這樣就算失敗）
- 講話像機器或像在念稿。
- 話太多：每經過一個招牌就開口。
- 一開口就講好幾分鐘（走路情境應短而精）。
- 用了按量計費的 LLM API，或在使用者不知情下產生 Google 費用。
- 額度用完時改用其他付費方式繼續。

## 5. 架構【我的提案】

> 注意：使用者最初說「這次不透過 server api，而是透過 openab」，原意是**不要按 token 計費的 LLM API**。由於 TTS、驗收、Google Places 代理、快取都需要放在家中主機，主機上勢必有一個我們自己的服務。這一點請使用者在核准時確認。

```
iPhone（Flutter App）
  ├─ 定位、時機判斷、播放佇列、背景音訊、鎖定畫面控制
  ├─ 語音辨識（iOS 裝置端，zh-TW）
  └─ 拍照
        │  私人網路（建議 Tailscale【我的提案】，不對外公開）
        ▼
家中主機（M3 → M6，macOS 原生）
  ├─ Buddy Host 服務（Python，新寫；可移植舊 backend 的部分邏輯）
  │    ├─ 景點探索：Overpass、Wikipedia geosearch、Google Places 代理（API key 只放主機）
  │    ├─ 內容準備編排：決定為哪些景點準備內容 → 請 openab 研究與寫稿
  │    ├─ 寫稿前處理：數字轉中文、去假名、切句
  │    ├─ TTS：KittenTTS 2（MPS）
  │    ├─ 自動驗收：Whisper 轉回文字比對 CER，失敗換 seed 重做
  │    ├─ 快取：景點資料、稿子、語音檔
  │    └─ 對手機提供 API：位置回報、取得待播內容、提問、拍照提問、額度狀態
  └─ openab → Claude Code（Claude Pro 訂閱）
       └─ 工具：WebSearch、WebFetch（查網路、Wikipedia）
```

**分工原則**：
- 手機負責「什麼時候講」（時機、播放、使用者互動）。
- 主機負責「講什麼」（查資料、寫稿、合成、驗收、快取）。
- 手機只連 Buddy Host 一個入口，不直接連 openab【我的提案】。這樣額度錯誤、快取、延遲控制都集中在一處。builder 若評估後認為讓手機直接走 openab 的 ACP WebSocket 更好，可以提出。

**openab 的部署**：openab 官方文件以 Docker、Kubernetes、ECS 為主。它能否在 macOS 原生執行，或在容器內執行並呼叫主機原生的 Buddy Host，**目前未知**，列為第一批驗證任務（第 13 節）。

**openab 是手段，不是目的**【使用者決定】：使用者要的是「用 Claude Pro 訂閱、不按量計費」。若 openab 驗證失敗，例如無法部署、連線不穩，或無法傳圖片，改由 Buddy Host 直接以 headless 模式（`claude -p`）呼叫 Claude Code，同樣使用訂閱。Buddy Host 與 LLM 之間的介接要做成可替換的一層，兩條路都能接上。

## 6. 好友的個性與寫作規則

### 個性【使用者決定】
以使用者自己寫的「名花之里」導覽稿為範本：原文在 `docs/spikes/2026-10-18-kittentts2/texts/35_nabana_original.txt`，套用第 6 節寫作規則前處理後的版本在同目錄的 `35_nabana.txt`。

1. 用「我們」，是一起旅行的同伴，不是站在台上的導遊。
2. 記得這趟剛去過哪裡，會拿來對比串連（「如果說剛剛的犬山城是……」）。
3. 有自己的看法（「最浪漫的瞬間，我覺得是……」）。
4. 先講有趣的反差或故事，數字只點到為止。
5. 給實用建議（幾點來最好、待多久）。
6. 知道什麼時候閉嘴。
7. 偶爾反過來問使用者，但要非常節制。
8. 聲音是女生（F2 參考錄音）。

### 長度
- 主動介紹預設每段 30～45 秒【我的提案】，理由是走路每分鐘約 70 公尺，且 M3 合成很慢。
- 使用者想多聽時，再展開。

### 寫作規則（試聽實測得出，Buddy Host 必須強制執行）
這些規則同時寫進給 Claude 的寫稿指示，並在 Buddy Host 的前處理裡用程式再保證一次：

| 規則 | 原因（見 spike） |
|---|---|
| 所有數字轉成中文（年份逐字讀「二零二七年」，數量用「兩百公尺」） | KittenTTS 2 對非英文必須 `normalize=False`，阿拉伯數字會亂唸 |
| 長串日期、多個數字的句子要拆短或改寫成口語（「十月中到明年五月底」） | 長串日期 4 次全敗，其中 2 次產生 40 秒亂碼 |
| 移除日文假名，必要時只留羅馬拼音 | 模型多半唸不出假名 |
| 避免「欸、啊、喔、吧、一下下」等語助詞；親切感靠句型和用詞 | 這些詞會讓模型跑成類粵語腔（轉簡體無效） |
| 英文單字盡量少用，能用中文就用中文 | 夾英文聽起來怪 |
| 依「。！？」切句，每段不超過約 90 字 | 內建切句只認 ASCII 標點 |

**待 builder 完成**：哪些語助詞是安全的（安全清單），要用驗收器做一輪批次實測後決定。使用者自己的稿子裡有「哇」「對了」「而且啊」，其中「哇」「對了」在名花之里測試中大致可接受，但未系統驗證。

## 7. 主動介紹流程

0. 按「出發」時，先把起點周邊一整區的內容準備好【我的提案，使用者同意】。這是依「當下所在位置」準備，不違反「不做預先規劃行程」的非目標，可以緩解 M3 合成太慢的問題。
1. 手機在背景持續定位，定期把位置與行進方向回報給 Buddy Host。
2. Buddy Host 找出附近候選景點（OSM + Wikipedia），依「行進方向前方、有 Wikipedia、距離近、不重複主題」排序。舊 backend 的 `services/poi_selector.py` 規則與 `services/poi_filter.py` 的過濾可移植。
3. 只為最有可能經過的前 1～2 個景點準備內容【我的提案】：請 openab 一次研究整個區域（同一輪查好幾個景點，省額度），寫稿、前處理、合成、驗收，存進快取。研究結果留在該趟旅程的 Claude 對話記憶中，供之後問答使用。
4. 手機在合適時機播放。舊 Flutter 的時機規則可作為起點：倒數循環、移動距離過小與候選重疊時跳過、24 小時內不重複、佇列內容過時就丟。
5. 沒有好內容就安靜。

**同一趟旅程的上下文**：好友要記得「剛剛去過哪裡」。實作方式（openab session 持續整趟，或由 Buddy Host 每次附上行程摘要）留給 builder。

## 8. 問答流程

1. 使用者發問。第一個里程碑用**螢幕上的按鈕**（按住說話）【使用者決定】。同時驗證「耳機按鍵觸發錄音」在 iOS 背景是否可行，例如 AirPods 或鎖定畫面的媒體控制，作為下一步。喚醒詞不在這個里程碑的範圍內。
2. 手機用 iOS 裝置端語音辨識轉成文字【我的提案】：免費、快，不佔主機。
3. 手機立刻播放事先合成好的短句（例如「好，我來查一下」）。這些短句事先跑多個 seed，由使用者挑選後存在 App 內。
4. Buddy Host 把問題連同目前位置、方向、附近景點清單交給 openab。優先用對話中已有的研究結果作答；需要時才上網查。
5. 回答的第一句要短（例如「那是龍山寺，主要拜觀音」），合成好就先播，後面邊播邊合成。
6. 吃的問題：Buddy Host 呼叫 Google Places，再交給 Claude 整理成好友口吻。
7. 拍照提問：手機上傳照片，Buddy Host 交給 Claude 看圖判斷。

### 延遲
- **目標**：從問完到聽到真正的答案 ≤ 10 秒（使用者可接受的上限）。要上網查的問題可以超過，但先說「我上網查一下」。
- **10 秒不是第一個里程碑的驗收條件**。在 M3 上，合成一句 3 秒的話就要 10～12 秒，加上驗收每句 3～14 秒，目前達不到。要靠 M6、llama.cpp 版本（`KittenML/kitten-tts-2-cpp`，beta）、參考錄音只編碼一次等優化。
- **問答的回答也要經過自動驗收**【使用者決定】：品質優先於速度。等待時間靠事先合成的短句填補。第一句是「好，我來查一下」；若真正的答案還沒好，再補第二句，例如「我想想怎麼說比較好」。這類短句都由使用者從多個 seed 版本中挑選。

## 9. 語音管線

- 引擎：`kittenml` 的 KittenTTS 2，`weights="packed"`、`decoder="default"`，裝置用 MPS。不要用 CPU：CPU 上 RTF 約 21，而且輸出異常。
- 參考聲音：F2 片段（`ref_24k.wav`，13.4 秒）加上逐字稿，存放在主機本機的 `~/.buddy-host/voice/F2/`，不入 git。**必須傳 `reference_text`**，否則套件會下載 Whisper 並用英文轉錄。
- 參考錄音的使用限制：
  - 取自公開 Podcast，是公眾人物的聲音，**只限使用者本人使用**。
  - **音檔不得進 git**，放在主機上的本機路徑，用設定檔指定。
  - 若 App 將來給任何其他人用，必須換成有授權的聲音。
- 自動驗收（spike 已實作原型 `run_r3_autocheck.py`）：
  - 逐句合成。
  - 用 Whisper small 轉回文字，經 OpenCC 轉簡體並去標點後計算 CER。
  - CER > 0.20 就換 seed 重做，最多 4 次，取最佳。
  - **必修**：比對前要把阿拉伯數字和中文數字統一，否則日期、數量句會被誤判。
  - 仍不合格時怎麼處理（跳過該句、改寫該句再合成、或請 Claude 換個說法）留給 builder，原則是**寧可少講一句，也不要播出聽不懂的語音**。
- 固定短句：由使用者從多個 seed 版本中挑選後，打包進 App。
- 已知效能（M3）：首次合成 RTF 約 3～4；含重試約 11 倍；KittenTTS 2 與 Whisper 同一個 process 時峰值記憶體 11.8 GB。

## 10. 景點資料與 Google Places

- **景點**：Overpass API（遵守公用伺服器政策：設定可識別的 User-Agent、遇 429 要退避、並快取）+ Wikipedia geosearch（附合規 User-Agent）。舊 backend 的 `clients/overpass.py`、`clients/wikipedia.py`、`services/wikipedia_resolver.py` 可移植。
- **Google Places（只用於吃的）**：
  - API key 只放在主機上，不放進 App。
  - Nearby Search 預設只要 Pro 欄位（名稱、類型、座標）。評分、營業時間只對要推薦的少數店家另外查。
  - **GCP 防護（使用者要求）**：
    - 在 APIs & Services → Places API → Quotas，把每日請求上限調低（建議 50 次／天）。
    - 另設預算警示（例如 1 美元寄信）當第二道防線。
    - 預算只會通知、不會停止服務；配額才真的會擋。

## 11. 額度與成本

- Claude Pro 的實際額度（5 小時週期與每週上限）**未查證**。一趟 3 小時的散步可能用不完，也可能不夠，必須實測。
- 省額度的原則：一次研究整個區域、查過的不再查、寫稿用較省額度的模型（Sonnet 或 Haiku，如果 openab 或 Claude Code 允許指定）。
- 額度用完：Buddy Host 偵測到 Claude 的額度上限錯誤後通知手機。手機播放事先合成好的「額度用完了」，然後停止主動介紹與問答。
- 額度恢復【我的提案，使用者同意】：Claude 的 5 小時週期重置後，好友自動恢復說話，不會整天停擺。Buddy Host 要能偵測額度是否已恢復，例如定期用很輕的請求探測，或依錯誤訊息裡的重置時間判斷。
- **不設每趟用量上限**【使用者決定】：這個 Pro 訂閱也用於其他日常工作。使用者的目的之一，就是實測一趟散步會用掉多少額度、多久撞到上限。因此 Buddy Host 要**記錄每次 Claude 呼叫的用途、時間，以及可取得的用量資訊**，走完一趟後產出用量報告。
- Google Places 的費用由配額上限控制在免費額度內。

## 12. 舊 repo 的處理

- **專案留在這個 repo**【我的提案，使用者表示沒意見】。
- 可沿用的 Flutter 模組：`shared/location/*`、`shared/audio/audio_player_service.dart`（要改成播放主機下載的 WAV）、`shared/db/local_db.dart`、`shared/notification/*`、`shared/settings/*`、`shared/logging/*`、`shared/mic/*`。也可參考舊的時機規則與播放佇列概念。
- 要重寫的：旁白、問答、景點抓取的 provider（全綁舊的 SSE 後端），以及 `shared/backend/*`。
- 舊 `backend/`（FastAPI、Gemini、Cloud Run）整體淘汰。其中的 Overpass／Wikipedia client、景點選擇規則、句子切分，可移植到新的 Buddy Host。
- **注意**：
  - 播放佇列（`tour_playback_queue_provider.dart`）、`TourAudioHandler`（audio_service）、iOS／Android 背景設定的最新版本，目前只存在於 `feat/plan-b-flutter-app-mvp` 分支**尚未 commit 的工作區**。從 main 開新分支或 worktree 不會帶到這些檔案。
  - 舊背景播放是 Android 優先設計，iOS 要重新驗證。

## 13. 未驗證的依賴（第一批計畫任務）

這些不確定性可能推翻架構，應在寫產品程式碼之前先驗證：

1. **openab 能否在這台 Mac 上和原生 Python 服務共存**：原生執行，或在容器內並能連到主機服務。並確認 ACP `/acp` WebSocket 端點的狀態：它的 ADR 仍是 Proposed，單次 prompt 180 秒沒有輸出就逾時，也不確定是否包含在預設 image 裡。
2. **透過 openab 傳圖片給 Claude**，供拍照提問使用。
3. **Claude Pro 額度實測**：研究一個區域、寫一段稿、回答一個問題，各用掉多少額度；額度上限錯誤長什麼樣、Buddy Host 怎麼偵測。
4. **16 GB 記憶體能否同時跑完整套**：openab、Claude Code、KittenTTS 2（實測 8.8～11.8 GB）、Whisper、Buddy Host。若不行，評估換更小的 ASR、分時載入，或等 M6。
